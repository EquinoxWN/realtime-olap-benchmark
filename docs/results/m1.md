```bash

olapbench gen --suite tpch --sf 0.1 --seed 42 --out .tmp/data/tpch-0.1   # 787,123 rows in 16.7 s
```

## Analyze and improve: thread count on a shared machine

The default run had a median hot coefficient of variation of 0.20 (SSB) and 0.21 (TPC-H), and on
four queries the hot median was slower than the cold one (Q3.2, Q4.3, Q10, Q18), which a warm
cache cannot explain. Root cause: DuckDB starts 20 threads for queries that last tens of
milliseconds, while about ten other builds share the CPU, so thread scheduling dominates the
timing. The same data was rerun with `--threads 4`:

| Run | SSB hot geomean | SSB median hot CV | TPC-H hot geomean | TPC-H median hot CV |
|---|---:|---:|---:|---:|
| DuckDB default (20 threads) | 31.1 ms | 0.20 | 35.4 ms | 0.21 |
| `--threads 4` | 16.2 ms | 0.11 | 11.4 ms | 0.10 |

At this scale fewer threads were both faster and steadier. The second run came after the first,
so the OS page cache was warmer; the cold medians (SSB geomean 25.8 ms, TPC-H 16.0 ms) improved
too, which points the same way. Files: `results/local/*-threads4.json`,
`results/local/report-threads4.md`. Thread count is therefore recorded in every result file and
shown in the report line of each engine; CI runs each engine with its defaults on an otherwise
idle runner.

## Server engines: CI only (not run on this machine)

ClickHouse 26.3.60.2, Apache Doris 4.1.3 (FE and BE images) and StarRocks 4.1.6 (all-in-one)
run in the `engines` job of `.github/workflows/ci.yml`, one at a time on the same GitHub runner
(`scripts/bench_servers.sh`), followed by DuckDB, with the Linux page cache dropped before each
cold run and `olapbench report --strict` failing the job if any engine's answer differs. Images
are pinned by digest in `docker/compose.yml`. Docker is not used on this machine (several
builds share it), and the repository has not been pushed yet, so **the engines job has not run
and there are no server numbers yet**; their adapters are covered locally by the protocol tests
in `test_engines.py` only.

Engine settings recorded in each result file:

| Engine | Deployment | Table layout | Cold run clears |
|---|---|---|---|
| DuckDB | embedded in the harness process | plain tables, `COPY` load, `CHECKPOINT` | DuckDB buffer pool (file reopened); page cache with `--drop-os-cache` |
| ClickHouse | `clickhouse/clickhouse-server` container, 6 GB limit | MergeTree ordered by first column, `OPTIMIZE FINAL` after load, `use_query_cache=0` | `SYSTEM DROP` mark, uncompressed, query, query condition, primary index and compiled expression caches (those the version supports); page cache |
| Apache Doris | FE and BE containers, host network, 6 GB and 6 GB limits, FE heap capped at 4 GB | duplicate key on first column, hash buckets 4 (fact) or 1, one replica, `ANALYZE ... WITH SYNC` | SQL and query cache off for the session; page cache (BE page cache cannot be cleared by SQL) |
| StarRocks | all-in-one container, 9 GB limit | same as Doris, `ANALYZE FULL TABLE` | query cache off for the session; page cache (BE page cache cannot be cleared by SQL) |
